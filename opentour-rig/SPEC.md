# OpenTour

## v0.6 — Полезный выход и непрерывное развитие

Миссия выполняется через работающий путь менеджера: данные CRM, реальные задачи/ответы/решения и проверенные кампании в пределах авторизации. Процедуры и документация обслуживают результат. Локальный технический blocker не останавливает весь проект; отсутствие заданий в очереди не доказывает отсутствия полезной работы. Lead поддерживает ближайшие исполнимые шаги и независимые потоки по действующим требованиям.

Инфраструктурный компонент, устраняющий наблюдаемое препятствие или повторяемую потерю времени, имеет обязательный приоритет разработки, функциональной проверки, исправления, интеграции и применения перед работой, продолжающей нести эту потерю. Предложение внутри мандата сразу получает владельца/следующее действие; отдельного пользовательского поручения на каждую внутреннюю доработку не требуется. Завершение — фактическое использование потребителем, не исходники или отчет. Функциональная независимая проверка сохраняется.

Техническая локальная проверка может использовать ограниченный временный application read-grant по PLATFORM v0.6; это не назначение реального менеджера и не новый внешний аккаунт. Native human identity, права reply/decision, CRM writes, send и deploy имеют собственные границы. Технический выбор инструмента/порта/синтетического тестового доступа не превращается в human gate. Реально недостающее полномочие эскалируется конкретно; остальные разрешенные части продолжаются.

v0.6 заменяет противоречащие агентские запреты в активных задачах, включая общее no-merge после уже разрешенного QA-led merge и запрет создать временный изолированный технический read-grant. История не переписывается; текущая задача получает явное основание изменения. Прямой пользовательский запрет не отменяется по предположению. Новых ролей/аккаунтов/моделей/провайдеров/внешних расходов не вводится.

## Миссия

OpenTour — локальный рабочий слой поверх готовых CRM, сервиса рассылок и OpenRig. Люди определяют намерение, проверяют материалы, общаются с клиентами и принимают зарезервированные решения; постоянные агенты готовят предложения, материалы и интеграции, исполняют поручения и накапливают проверяемый опыт. Не писать собственные CRM, АТС или движок рассылки.

## Первый пользовательский результат

Администратор через рабочий диалог обращается к существующему оператору ядра OpenRig и поручает работу. Менеджер с ролью user видит общую доску, импортированные записи физических лиц и организаций, краткую карточку со ссылкой в CRM и кампании. Все разделы и разрешённые диалоги доступны user для чтения; свободный ввод агентам доступен только administrator. Оба отвечают и добавляют уточнения через карточки задач. Поручение появляется на общей доске людей и агентов. Команда формирует предложение и HTML-email; менеджер просматривает драфт. Агент может запросить уточнение, валидацию или ручной шаг.
OpenTour DB сохраняет board tasks, запросы, ответы/комментарии и явные связи. Для релевантного контекста назначенному агенту БД хранит только lifecycle доставки сообщения: enqueue, delivery attempt и terminal delivery receipt. Receipt terminal только когда закреплённая native очередь подтвердила принятие scoped context message, а возвращённый qitem ID сохранён как execution reference к board task/request. Это подтверждает handoff сообщения, не его прочтение или выполнение работы; неизвестный исход сверяется по стабильной delivery identity до повтора.
OpenTour DB не владеет execution ownership, progress или result задачи. Их источником остается OpenRig queue; UI может показывать только read-only projection native состояния. Сохраненный ответ — запись разговора, не native human decision и не полномочие выполнить бизнес-действие. Receipt доставки контекста также не завершает задачу и не разрешает действие.
После обновления страницы записи, ход работы и драфты не исчезают. Administrator настраивает пользователей/подключения, user не получает административный доступ.

Это работающий локальный информационный слой, а не UI-демо с симулированным чатом. Реальная массовая отправка, новая VPS и телефонная смена не входят в первую приемку. Не скрывать fixture-adapter рассылки за статусом реального подключения. Доступное безопасное preview локального драфта обязательно, внешнее сохранение в настоящем сервисе — после идентификации сервиса и разрешенного доступа.

## UI-решения от 2026-11-09

Главный экран — общая Kanban-доска примерно на две трети ширины и раскрывающаяся панель справа. Карточки представляют понятную работу команды и действия человека, а не каждый мелкий qitem. Открытие — модалка наподобие Jira, ответы/уточнения только текстом. Drag-and-drop нет: при live-смене статуса карточка вертикально сжимается в исходной колонке и расширяется в целевой; ввод и открытая модалка сохраняются.

Контекст разделов: Задачи — оператор ядра; Клиенты — Creative; Кампании — оператор кампаний. User читает историю, но пишет только через доступные задачи. Кампании гибкие: полный пакет с аудиторией и материалами email/SMS/обзвона. Email остаётся первым интеграционным приоритетом; SMS/обзвон представлены в UI без обязательного подключения на первом этапе. Жёсткий линейный мастер и дополнительные стадии утверждения не вводятся.

Узкий UI-прототип оценивает понятность экранов на явно обозначенной синтетике. Реальный информационный слой по-прежнему требует работающих CRM/kernel-интеграций. Источники UI-требований: [UI flow](../docs/UI_FLOW.md) и [архитектура](../docs/ARCHITECTURE.md).

## Источники истины

CRM владеет клиентскими записями; mailer — фактами кампаний/отправок/отписок; телефония — звонками. OpenTour DB владеет app-facing board tasks, запросами, ответами/комментариями, явными связями и только lifecycle доставки релевантного агенту контекста (enqueue, delivery attempt, terminal receipt). Terminal receipt означает подтверждённое native очередью принятие сообщения с сохранением qitem ID; он не подтверждает прочтение, выполнение, завершение задачи или разрешение действия. OpenRig queue владеет execution custody, execution ownership/progress/result и native action evidence; qitem IDs ссылаются на исполнение, но не восстанавливают разговор. UI может показывать native execution state только как read-only projection. Рабочая доска не является CRM и сохраняет явные ссылки на источники фактов. До импорта источниками фактов служат неизменные пользовательские файлы, затем сохраненная lineage к CRM.
